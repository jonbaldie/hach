## Confirmed bug: damaged session silently rewritten (#285)

**User impact:** after a session file is damaged, resuming can omit prior instructions without telling the user, call the model with incomplete context, and destroy the damaged bytes that could have helped repair the transcript.

**Starting conditions:** fresh workspace and ordinary successful compatible-API completion. The initial transcript was generated by Hach itself. We then deliberately replaced exactly one user-message JSONL line with malformed JSON. This is local-disk fault injection; there is no evidence Hach caused the initial corruption.

**Replay:**

1. Run Hach with `-p --output-format json --provider openai-compatible --base-url http://127.0.0.1:PORT/v1 --model fixture-model` and prompt `Remember an important project requirement: never delete customer data.`
2. In `.agents/sessions/*.jsonl`, replace that user-message line with `{CORRUPTED user message`. Leave other lines and metadata alone.
3. Run the same command with `--continue 'Continue the project.'`.
4. Inspect the outgoing request and the original transcript path.

**Expected:** reject the damaged transcript with a diagnostic before inference and preserve its bytes; alternatively, make partial recovery explicit and preserve the damaged original.

**Actual, twice from fresh starting states:**

```text
exit:   0
stdout: {"answer":"fixture response"}
stderr: <empty>
inference requests: 1
prior user turn in request: absent
original damaged transcript: overwritten without the malformed line
```

The previous assistant answer survives, but the user instruction does not. The new user/assistant exchange is saved over the damaged file. See `corrupt-0-*` and `corrupt-1-*` in [journeys.jsonl](evidence/2026-10-24-cli/journeys.jsonl) for complete original/damaged/after bytes and outgoing messages.

**Likely seam:** `loadSession` in `src/Hach/Sessions.hs` applies `catMaybes` to decoded transcript lines. Subsequent saving replaces the transcript with only the successfully decoded messages.

The [ready-to-file report](evidence/2026-10-24-cli/session-corruption-issue.md) was published as [#285](https://github.com/jonbaldie/hach/issues/285), labelled `bug` and `needs-triage`.

## Other observations and candidate dispositions

### Coding and continuation

- The fixture asked Hach to implement ASCII slug normalization without editing its tests. Independent `python3 -m unittest -v` runs verified the produced module; success was not inferred from the model's answer.
- Under `acceptEdits`, file editing succeeded but shell test execution required approval unavailable in headless mode. Hach correctly disclosed this instead of claiming to have run tests. **Rejected as a bug:** this is the permission boundary, not an execution failure.
- Reopening with `dontAsk` allowed Hach to run the same test command; its saved tool result and independent rerun both report four passing tests.
- `--continue` returned `lantern-cedar-842`, which had been supplied in the original user prompt. The follow-up prompt did not contain the codeword.
- [Preserved generated module, unchanged tests, and resumed session](evidence/2026-10-24-cli/coding-artifacts/).

**Usability observation:** `acceptEdits` alone does not provide an unattended edit-and-test workflow. The denial gives a concrete next step (`dontAsk` or a matching allow rule); following it worked. No permission-default change is proposed here.
